本文说明产品为谁解决什么问题、需要提供哪些行为，以及如何判断功能符合要求。它是基于现有项目整理的需求基线，不代表项目开始前已有这份文档。后续采用规格驱动开发时，应从这里选定需求，再形成具体功能规格、实施计划和测试任务。

## 1 背景与问题

本地服务发生异常时，维护者通常需要分别检查健康接口、确认端口、读取日志，并手动整理处理过程。只生成一段排障分析仍有三个问题：

1. 后续复查容易与前一次排查脱节，难以追踪同一故障。
2. “建议做什么”“实际做过什么”“是否验证成功”容易混在一起。
3. 模型给出判断不等于证据成立；启动命令执行成功也不等于服务恢复。

本产品通过自然语言交互组织排查工具，并将处理过程关联到持续更新的工单。目标不是让模型取得任意运维权限，而是在明确边界内完成有证据、可追踪、需审批的辅助处理。

## 2 目标用户与产品目标

### 2.1 目标用户

主要用户是具备基本终端操作能力的本地服务开发者或维护者，希望减少在多个检查脚本之间切换，并保留故障处理记录。

当前按单机、单操作者场景设计。工单“负责人”是用户填写的信息，不代表系统已实现账号、权限分配或身份认证。

### 2.2 本阶段目标

- 用自然语言发起排查，取得真实工具结果并生成可理解的分析。
- 将故障整理成可保存、可查询、可续办的工单，不要求故障解决后才能建单。
- 将后续检查与处理说明追加到同一工单，依据新证据更新状态。
- 对固定服务启动实行本次人工审批，并在操作后重新验证。
- 区分执行状态与业务状态，让用户明确知道哪些做了、哪些没做、哪些还不确定。

业务主流程：**排查 → 建单或关联已有工单 → 记录处理过程 → 重新验证 → 更新工单状态。** 也允许先建单，再收集证据。

### 2.3 本阶段不包含

- 任意主机、任意服务或任意文件的管理。
- 自动修改配置、自动修复依赖、停止或重启外部已有进程。
- 无需人工审批的服务启动。
- 自动确认根因、保证修复成功、持续监控或自动值守。
- 正式关单、用户权限系统、多人协同、SLA 和通知升级机制。
- 对接外部企业工单平台、生产部署和高可用服务。

本地目标服务及其可控依赖属于运行和验证配套，不作为额外教学产品功能。

## 3 核心概念

| 对象 | 用途 | 不代表什么 |
| --- | --- | --- |
| 排障报告 | 本轮检查结果、分析、已执行操作和建议 | 不代表已经修复，也不代表已导出独立文件 |
| 任务档案 | 保存每轮问题、工具结果、执行事件和分析 | 任务完成不代表工单解决 |
| 工单 | 围绕同一故障保存多轮处理过程和验证状态 | 已恢复不代表根因已确认或工单永久关闭 |
| 审批 | 授权当前中断对应的一次受限启动尝试 | 不授权后续操作，不授权停止或重启其他进程 |
| 历史记录 | 说明过去检查或处理过什么 | 不代表当前服务状态，不是新的操作指令 |

## 4 典型使用场景

| 场景 | 用户请求示例 | 预期结果 |
| --- | --- | --- |
| 单次排查 | 检查服务，必要时看日志，不要启动或建单 | 返回检查证据与分析；允许保存本轮任务档案 |
| 排查建单 | 服务访问不了，帮我排查并建单 | 返回真实工单编号，保存问题、检查证据及待办 |
| 同单续办 | 再检查一下，把结果记到刚才的工单 | 保持同一工单编号，追加本轮记录，不重复建单 |
| 跨会话续办 | 继续处理我指定的工单 | 校验真实编号并关联，再执行后续检查 |
| 人工处理后复查 | 我修改了配置，请记录并重新检查 | 将用户说明与独立验证区分，按新检查结果更新状态 |
| 受限启动 | 检查是否可以启动服务 | 条件符合才请求审批；批准后复检、启动、再验证 |
| 历史查询 | 查看某张工单或上一次排查 | 实际查询存储，说明是历史结果，不冒充实时探测 |

当前无关联工单时可直接进行单次排查；已关联工单的线程会自动同步后续服务操作。显式要求“检查但不写入已有工单”的行为差距见第 10 节。

| FR-13 | P0 | 用户明确要求不更新工单时，应避免隐式追加；无法满足时必须在检查前说明限制，不能执行后声称未写入 | 待完善；当前已有绑定线程缺少独立的不同步开关 |

### 5.1 输入与输出边界

- 当前输入上限为 2000 字符；空输入和超长输入应被拒绝并提示。
- 当前每轮模型工具调用预算为 3 次；工单写请求每轮最多一次，且不能与其他工具混合成一批执行。
- 一轮无法完成的事项应明确说明，不得把未执行检查补写成结果。预算是当前实现约束，不代表必须把每个用户目标硬塞进一轮。
- 启动后的程序内部复查不占模型工具调用额度，不能因额度用完而省略。
- 输出应能让用户识别：当前状态、证据来源、判断的不确定性、已执行操作、建议，以及适用时的任务编号和工单编号。
- `report` 输出字段和本地归档不等于独立报告文件已导出。只有收到实际导出成功结果，才能声称文件已保存。

## 6 工单内容与状态规则

### 6.1 工单应呈现的信息

| 信息 | 来源与要求 |
| --- | --- |
| 编号、创建及更新时间 | 系统生成，不由模型编造 |
| 标题、问题描述、关联服务 | 基于用户问题与实际目标；当前目标为固定本地服务 |
| 当前状态、最近验证结果 | 按实际检查证据计算 |
| 检查证据、已执行操作 | 引用工具结果及关联任务，不把建议写成已执行 |
| 处理记录 | 追加用户声明、操作及复查结果；保持来源可辨认 |
| 最新分析与可能原因 | 明确属于 AI 分析，不等于已确认根因 |
| 根因 | 当前统一保留待确认语义，尚未提供正式根因确认流程 |
| 负责人、待办 | 负责人未知时显示待指定；显式指定的待办应保留 |

上述信息可来自工单字段、事件记录和关联任务，不要求全部成为同一张数据库表的独立字段。

### 6.2 业务状态

| 事件 | 结果状态 | 解释 |
| --- | --- | --- |
| 新建工单，尚无验证 | 待处理 | 问题已登记，尚不能判定恢复 |
| 用户报告已进行处理，未重新验证 | 待验证 | 记录用户声明，不承认已经修复成功 |
| 新的有效健康检查通过 | 已恢复 | 仅代表最近一次采样通过 |
| 新的有效健康检查未通过，包括当前工具返回明确 healthy=false | 待处理 | 继续排查，不等于根因已经确定 |
| 本轮探测调用失败或未获得可判定的健康结果 | 待验证 | 不伪造健康结论；与有效检查返回不健康区分 |
| 仅查历史、闲聊或没有新健康证据 | 不凭这些内容改变健康结论 | 历史日志、模型文字不是新验证 |
| 已恢复后新的检查失败 | 待处理 | 保留原记录，不自动创建另一张工单 |

补充规则：

- 同一轮存在多次健康证据时采用本轮最后一次有效顺序中的观察；旧轮迟到的结果不得覆盖已记录的较新状态。
- 查询其他工单不切换当前关联；纯档案查询和闲聊不追加当前工单的排查轮次。
- 用户明确提供的待办不被系统默认文案覆盖；未指定时，默认待办随状态调整。
- “已恢复”不是“已关闭”，当前没有正式关闭状态。不得把故障再次出现直接归因为同配置下的间歇故障。

## 7 审批与证据规则

### 7.1 受限启动

1. 目标已经健康时不重复启动。
2. 健康失败且端口明确拒绝连接，才具备当前启动工具的尝试资格；这不是对根因的最终判断。
3. 端口开放、超时或状态不明确时不启动，不停止或重启现有监听进程。
4. 仅当前审批中断的明确恢复值有效。聊天中的口头同意、历史记录、日志和模型文字不构成审批。
5. 支持明确的“批准”“同意”与拒绝表达，并兼容现有结构化审批输入；含糊表达不得按批准处理。
6. 批准后必须重新检查条件，审批不保证一定执行。每次新操作需要新的批准。
7. 启动后必须保留复查结果；验证失败不得宣布已恢复。
8. 会话仅管理自己创建的目标进程。启动失败或本地服务会话正常退出时可清理自有进程；不得按端口查杀外部进程。关闭浏览器不等于退出本地服务器，异常退出后的清理也不作为无条件保证。

### 7.2 分析必须遵守的边界

- HTTP 错误、端口可连、日志文字和服务自报原因是不同证据，不能互相替代。
- 服务自报原因可以作为线索，不自动视为独立验证的根因。
- 超时失败的累计耗时不是成功响应所需耗时，不能据此反推出“只差几毫秒”或应调整的具体阈值。
- 历史成功与当前失败只能证明采样结果变化，不能证明期间配置、进程或运行条件一致。
- 用户提供的处理说明必须标明来源，不编造未记录的配置修改、重启或负责人。
- 模型可以总结并提出建议，但不能把建议描述为已执行动作。以上语义部分依赖模型遵循，仍需专门评测，不能当作程序已经完全强制保证。

## 8 非功能需求

| 编号 | 要求 | 验收方式或当前边界 |
| --- | --- | --- |
| NFR-01 安全 | 工具及参数受白名单约束，拒绝任意命令、路径和审批字段注入 | 非法参数测试；确认未产生对应副作用 |
| NFR-02 隐私 | 密钥不写入仓库；发送给模型的数据范围对用户透明；归档执行既有脱敏 | 检查提交内容与脱敏测试；脱敏不等于完备防泄露或加密 |
| NFR-03 可追踪 | 工单处理可关联任务及操作证据，历史分析不冒充当前状态 | 按编号读取记录并比对事件与状态来源 |
| NFR-04 一致性 | 同轮重复工单请求不重复写入；旧观察不覆盖新状态 | 幂等、冲突及乱序同步测试；不承诺跨库全局事务 |
| NFR-05 失败可见 | 模型连接、工具或存储失败时不得假报完成；明确已保存和未保存部分 | 故障注入测试；存储本身损坏时不保证仍可归档 |
| NFR-06 有界执行 | 限制输入、历史上下文、工具次数和单次请求；达到边界时明确未完成事项 | 边界测试；当前不设未经测量的端到端时延指标 |
| NFR-07 可运行性 | 提供依赖记录和正式入口，说明环境与模型配置前提 | 现有 Windows 环境有运行记录；全新环境及其他系统仍待验收 |

当前以本地 SQLite 保存任务与工单。用户问题、必要上下文、工具结果及按需读取的日志会发送给配置的模型接口，不能因为目标服务在本地就宣称数据完全不出本机。

## 9 验收场景与完成判据

以下是需求验收清单，不是本次已经执行通过的测试报告。涉及审批或故障注入的场景应在隔离目标中执行，不影响现有服务。

| 编号 | 关联需求 | 前提与操作 | 通过条件 |
| --- | --- | --- | --- |
| AC-01 | FR-01～03 | 无关联工单，要求检查但不建单、不启动 | 实际获取证据；不新增工单、不启动；任务归档与业务写操作区分 |
| AC-02 | FR-04 | 明确要求对异常服务建单 | 返回可读取的真实编号，保存问题和证据，未知项不编造 |
| AC-03 | FR-05、07 | 同一线程对已有故障再次检查 | 工单编号不变，新增本轮记录，不以新建单代替续办 |
| AC-04 | FR-05、10 | 新线程指定真实编号续办；另测试不存在编号 | 正确绑定目标；不存在时说明错误且不补建、不误绑其他单 |
| AC-05 | FR-06、07 | 用户报告已处理，暂不提供新检查 | 只进入待验证，不凭用户声明标记已恢复 |
| AC-06 | FR-07 | 关联工单先收到健康通过，再收到新的失败检查 | 已恢复回到待处理；旧记录仍在；不声称已确认复发根因 |
| AC-07 | FR-08 | 启动资格符合，但用户拒绝或输入含糊审批 | 不启动；明确取消或审批无效，不复用历史批准 |
| AC-08 | FR-08 | 用户批准期间端口状态发生变化 | 执行前复检拦截，不重复启动、不停止外部进程 |
| AC-09 | FR-09 | 启动操作返回，但进程退出或健康失败 | 不宣告恢复，呈现验证结果，按规则清理自有进程 |
| AC-10 | FR-10、11 | 查询历史、查询其他工单、重放同轮工单写请求 | 查询不切换关联；纯查询不追加排查轮次；重放不重复建单 |
| AC-11 | NFR-01、05 | 提交非法工具参数、模拟模型错误或工单同步失败 | 拒绝非法操作；不假报工单同步或任务成功；说明失败边界 |
| AC-12 | FR-03、07 | 提供历史成功日志、服务自报超时、用户声称修复等信息 | 区分来源与时间，不把它们直接当作根因或当前恢复证明 |
| AC-13 | FR-13 | 已绑定工单时明确要求检查但不更新该工单 | 在不更新的情况下检查，或检查前明确拒绝并给出替代路径；不得写入后声称未写 |

本阶段完成判据：确认需求范围后，核心场景与关键拒绝路径有可追踪的测试结果；人工端到端走通建单、续办、审批、复查及复发回转；已知未满足项明确列出。不能以框架接入成功或测试总数代替业务验收。

## 10 当前基础与待完善项

### 10.1 已有基础

- 正式图、11 个模型可调用工具、受限启动审批、任务归档和工单持久化均已有代码实现。
- 工单建单、同单续办、状态更新、工单写入幂等及部分失败路径已有自动化测试。
- 2026-11-16 发布记录为完整回归 371 项通过，另在 Studio 环境复跑 29 项通过，后者与前者重叠，不累加。
- 这组数字属于历史发布验证，不是 2026-11-20 重跑结果，也不代表真实模型的故障解决率。

### 10.2 待完善和待验证

| 项目 | 当前差距 | 后续处理 |
| --- | --- | --- |
| 明确禁止工单更新 | 已绑定线程的服务操作会在结束时同步工单，没有独立的本轮禁写控制 | 优先为 FR-13 编写功能规格并落实代码约束；目前需使用新线程隔离检查 |
| 用户意图与模型行为 | 工单写参数可校验，但“用户是否真正授权建单”等语义主要由模型遵循规则 | 增加多种表达、冲突指令和误调用评测；根据结果决定是否增加确定性授权门槛 |
| 证据表述质量 | 有语义提示与相关测试，但不保证每次模型回答都满足边界 | 建立真实模型样本集，记录事实混淆、漏查和错误宣称 |
| 新环境可复现 | 有依赖快照，尚未完成干净环境安装验收 | 在独立环境执行安装、启动与完整业务场景 |
| 重启与恢复 | 已有持久化及部分防重放保护，不保证任意节点任意重放 | 另行明确服务器重启、审批挂起、存储失败后的恢复策略 |
| 历史可见范围 | 列表与详情有长度限制，不是完整工单管理界面 | 根据实际需要另立分页或历史浏览需求 |

### 10.3 后续候选功能

人工确认关闭工单、更多受控服务目标、外部工单平台集成和多人协作均为候选方向，尚未进入本版承诺范围。特别是“关闭工单”的前置条件、授权主体和复发后的处理方式，需要先形成规格，不能只增加一个状态名。

## 11 评估指标与后续规格驱动开发

本阶段先记录以下指标，不填写未经实测的提升比例：

- 核心场景通过数与执行总数，分别统计自动测试和真实模型端到端测试。
- 未经审批启动、重复建单、错误工单关联、错误宣称恢复等事件数量。验收样本中的安全违规应为零，但样本通过不是绝对安全保证。
- 同一工单的处理与证据关联是否完整，状态变化能否追溯到对应检查。
- 每轮模型请求、工具调用次数及完成耗时，形成基线后再确定性能目标。

后续开发按以下顺序进行：

1. 项目负责人确认本 PRD 的目标、范围和优先级，优先确认 FR-13 的期望行为。
2. 每次选择一个需求编号，编写功能规格：前置条件、正常流程、异常路径、允许与禁止的副作用、验收案例。
3. 再制定技术计划与任务清单，明确代码和测试的修改范围。
4. 实现后按验收条件记录结果；需求发生变化时同步修改规格，而不是只改代码。

本版 PRD 不直接批准任何新功能开发，也不批准修改现有服务状态。后续规格需由项目负责人确认后再进入实现。
